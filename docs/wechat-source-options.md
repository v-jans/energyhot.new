# 公众号信源替代方案选型报告

> 调研日期：2026-11-17 · 适用项目：hot-news · 前置结论：[wechat-article-spider 可行性诊断](./sources.md)
>
> 目标：找出可直接用或可改造的公众号内容获取方案，围绕**降本增效**给出替代路径、优先级与决策依据。
> 本文中所有 GitHub 元数据（star / 最后提交 / 归档状态 / License）均经 GitHub API 逐个核实；服务条款与覆盖清单经官方页面核实。

## 0. 执行摘要：推荐结论

**不要为了替换而新建采集应用。** 推荐一条分三步走的组合路径：

| 优先级 | 动作 | 开发量 | 月成本变化 | 主要收益 |
|---|---|---|---|---|
| **P0 立即** | 修正 6 个 `wxid` → `ghid`，核对实际产出与预算上限 | 0（改配置） | 最多止损 **¥310.80/月** | 先确认「付的钱有没有买到数据」 |
| **P1 并行** | 用官网 `web_list` / `rss` 扩源，替换 6 个 T2 行业媒体号 | 0（加信源） | 再降 **约 ¥310.80/月** | 零风控、零合规风险，数据质量更高 |
| **P1 试点** | 选 2 个号双跑自建 RSS 网关，验证凭证与时效 | 中（部署+适配） | 试点期不省钱 | 拿到真实运维成本后再决策 |
| **P2 条件触发** | 仅在「必须去第三方付费依赖」时，全量迁自建 | 中高 | 降至 **¥0 付费** | 去掉按次计费，但引入凭证与风控负担 |

**核心判断**：现有 8 个公众号号的付费上限是 **¥436.80/月（¥5,314.40/年）**，这是一笔有天花板的钱；而自建 RSS 网关最大的卖点是「全文输出」——恰恰是 hot-news 合规规则明令不公开的部分。**用一个会带来凭证过期、账号风控、时效退化的系统，去省一笔每年五千元、且已有一大半可能是空转的支出，ROI 未必为正。**

**明确排除**：Wechat2RSS（用户协议禁止商用）、RSSHub 微信路由（依赖第三方镜像 + 每日约 15 次限额）、WechatSogou / 搜狗系（2019 年后无实质代码提交，README 自承接口被屏蔽）、wewe-rss（已归档）、wechat-article-spider（上一轮已判定不满足生产要求）。

### 1.3 ⚠️ 已发现的空转风险

`docs/sources.md` 第 208、213 行明确要求 `mp_account` 的 `config` 写成 **原始 ID `gh_` 开头的 `ghid`**，并特别注明「不要写成 `biz` / `name`」。`config-keys.ts` 虽然同时允许 `wxid` 和 `ghid`，但 `sources/mp.ts:45` 是 `source.config.ghid ?? source.config.wxid` 直接把值塞给 Dajiala 的 `ghid` 参数。

- **6 个号填的是微信号**（`tianheguangfu`、`PV-perspective`、`EnergyStorageMarket` 等），不是 `gh_` 原始 ID；
- 这 6 个号合计 **74 次/天 ≈ ¥310.80/月 ≈ ¥3,781.40/年**；
- 若 Dajiala 不认微信号，这笔钱可能是**纯空转**；若认，则文档与实现不一致，属于隐性技术债。

**这是本次调研中投入产出比最高的一条：不写一行代码，先查后台 `fetch_runs` 与健康状态即可定性。**

### 1.4 替换方案必须守住的硬约束

来自 `docs/sources.md`、`docs/customize.md`、`packages/backend/src/sources/rss.ts`、`packages/backend/src/ingest/items.ts`：

1. **合规**：`site_fulltext` / `syndicate_fulltext` **默认关闭**，只显示摘要 + 原文链接；原文明确写着「公众号、付费墙内容不会因为技术上抓得到就获得全文展示」。→ **自建方案最值钱的「全文 RSS」能力，在本项目里不能用于展示。**
2. **发布时间**：无可信 `publishedAt` 的条目不公开；旧文不会进入当日新闻。搜狗/镜像源常缺时间。
3. **参与方式**：`external` 推送接口自动建的源默认 `isolated`，需人工改 `editorial` 才进公开页。
4. **ingest 接口**：`POST /api/ingest/items` 用 `INGEST_TOKEN`（≥16 位），`INGEST_RATE_LIMIT` 限流，**≤50 条/次**；`ItemIn` 只有 `title / url / publishedAt / author / raw`，**没有正文字段**。
5. **RSS 正文判定**：`rss.ts:127` 要求 `bodyText.length > 280` 或 `summaryIsBody === true` 才认作正文，否则标记 `bodyStatus: pending` 并**回头去抓原文页**（`mp.weixin.qq.com`）——这是自建 RSS 接入时最容易踩的坑。
6. **可观测性**：现有 `mp_account` 链路已接付费回执、预算熔断、cursor、失败重试、`fetch_runs`、健康度、旧文规则。任何替代方案若绕开这些，等于用「省下的 ¥436」换掉整套治理。

### 2.2 三个「可直接使用 / 可改造」的候选详解

#### A. `rachelos/we-mp-rss`（WeRSS）— **改造后可用，推荐首选自建**

- **采集原理**：Docker 单容器 `:8001`，Python + FastAPI + Vue3 + SQLite/MySQL/PG。需**微信扫码授权**（`WechatAuthQrcode.vue`），`jobs/failauth.py` 监控凭证失效并通过钉钉/飞书/企微推送新二维码；支持 `wechat.allowed_accounts` 多账号轮换；`gather.model` 有 web / api / app 多采集模式。
- **能力**：标准 RSS 2.0 / Atom / JSON Feed，`RSS_FULL_CONTEXT` 全文开关，REST API + Access Key 鉴权，Webhook，定时（`SPAN_INTERVAL` 默认 10 秒级检查、`GATHER.CONTENT_AUTO_INTERVAL` 59 分钟补采），自定义 HTML 过滤规则，级联（父子节点）分布式。
- **许可**：MIT，可商用、可改造，无传染性。
- **维护**：最后提交 2026-11-10，5.2k star，活跃的中文社区项目。
- **风险**：凭证过期需人工扫码；采集依赖微信侧非公开接口，存在账号风控与规则变更风险；社区项目无 SLA；默认 `admin/admin@123` 需立即改。

#### B. `tmwgsicp/wechat-download-api` — **功能最全，但 AGPL 是硬约束**

- **采集原理**：Docker `:5000`，**微信公众平台后台扫码登录**，凭证自动写入 `.env`，**有效期约 4 天，过期需重新扫码**。反风控体系为 Chrome TLS 指纹模拟 + SOCKS5 代理池轮转 + 三层自动限频。
- **能力**：标准 RSS 2.0（含完整正文与图片）、`RSS_POLL_INTERVAL` 默认 3600 秒、REST API、内置 MCP（6 个工具）、7 种格式整号导出（Markdown/HTML/Word/PDF/EPUB/Excel/JSON）、图片代理解决防盗链、聚合源 `/api/rss/all`。
- **许可**：**AGPL-3.0**。若作为网络服务对外提供，会触发相应的源码开放义务；用于纯内部采集、不改动二进制分发时风险较低，但需法务确认。对「对外公开的 hot-news 站点」而言这是需要明确评估的一项。
- **维护**：2026-02 建库，最后提交 2026-07-27，近 4 个月无更新，项目较新、单人色彩强。
- **风险**：4 天凭证周期意味着**每月约 7~8 次人工扫码**，这是最容易被低估的运维成本；AGPL；明确以「规避微信风控」为卖点，规则变更时脆弱。

#### C. `ttttmr/Wechat2RSS` — **不可用，硬阻断**

- 仓库**只有 README 和公众号列表**，私有部署卖的是**闭源软件授权**（¥15/月、¥150/年），不提供部署服务；公开服务收录 300+ 号。
- **用户协议原文**：「**仅允许个人学习和研究使用，禁止商用和内容分发**」。hot-news 是对外公开站点，接入即违约。
- **覆盖度实测**：抓取 `https://wechat2rss.xlab.app/list/all/`，得到 **395 个 feed 链接 / 约 324 个公众号名**，分类为「安全 / 开发 / 其他 / 用户提交」，页面「安全」一词出现 116 次；**「光伏」「储能」「电力」「能源」「电改」及 7 个目标号全部 0 命中**。行业覆盖为零。
- **时效**：官方称尽力 24 小时内，私有部署平均 **6 小时**延迟——显著劣于现状的 60~240 分钟检查间隔。
- 结论：**双重不合格（许可 + 覆盖），不进入对比矩阵评分。**

### 2.3 为什么其余路线也不成立

- **RSSHub `/wechat/*`**：`lib/routes/wechat/` 下确有 12 个路由文件（`announce` / `ce` / `data258` / `ershcimi` / `mp` / `msgalbum` / `sogou` / `tgchannel` / `uread` / `wechat2rss` 等），但**全部依赖第三方镜像站或特定用途**，没有「按任意公众号名稳定订阅」的通用路由。官方器文档对 `data258` 标注「严格反爬」「每日阅读量限额约 15 次」「该限额足够订阅至少 3 个公众号」；`uread` 明说「并不是所有的都支持，能不能用随缘」；`mp` 只适用带 `homepage` 分享模板的号。`wechat2rss.ts` 只是把上面那个禁商用的服务再包一层。**8 个号的生产需求完全放不下。**
- **搜狗系（WechatSogou / Sougou-Wechat / wechat-article-spider global 搜索）**：WechatSogou README 的 FAQ 自承「**微信屏蔽此接口，请在临时链接有效期内保存文章内容**」「获取文章只能 10 篇」，代码停在 2019 年，README 顶部还挂着住宅代理广告。搜狗通道有验证码与限流，且只返回临时签名链接、发布时间常缺——会直接撞上 hot-news「无可信时间不公开」和旧文规则。
- **wewe-rss**：9.6k star 但仓库已 `archived`，基于微信读书接口，不再维护，不应作为新系统底座。

评分 1~5（5 最优），「合规风险」列为**风险高低**（低=好）。

**读这张表的三个要点**：

1. **现状在「稳定性 / 维护 / 部署 / 合规」四列全是 5**，只有「成本」一项是 3。替换方案必须证明它带来的成本节省，值得用四项满分去换。
2. **所有非付费方案的共同短板是「凭证 / 风控」**：它们本质都是拿一个微信个人号或公众号管理员身份去调非公开接口，只是把「按次付费」换成了「按人工扫码付费」。
3. **内容覆盖上，只有商业 API 和自建网关能精确覆盖目标 8 号**；免费公开服务在能源行业是空白。

## 4. 替代方案规划（围绕降本增效）

### 方案 0｜先止血：核对并修正现有 `mp_account` 配置 ✅ P0

- **适用场景**：任何后续决策之前，无条件先做。
- **动作**：后台「信源」页逐个查 8 个号的 `fetch_runs` / 健康状态 / 近 7 天产出 → 把 6 个 `wxid` 统一换成 `gh_` 原始 ID → 核对「设置 → 付费请求上限」是否被自适应调频推高。
- **预期收益**：确认或止损 **¥310.80/月（¥3,781.40/年）** 的疑似空转调用；同时避免自适应调频把账单推向上界 ¥3,225.60/月。零开发、零新风险。
- **主要风险**：若 6 个号本来就有产出，修正后成本不变——但这一步仍必要，因为消除了配置与文档的不一致。
- **优先级**：**P0，立即执行，且是后续所有方案的前置条件。**

### 方案 1｜去公众号化：用公开官网源覆盖同样的信息 ✅ P1 主推

- **适用场景**：6 个 T2 行业媒体号（北极星、智汇光伏、储能与电力市场、高工储能、南方能源观察、鱼眼看电改）。这些媒体多数有官网、官网有列表页或 RSS，内容与其公众号高度重合。
- **动作**：在 `industry/sources.json` 增配 `web_list`（CSS 选择器）或 `rss` 源；`docs/sources.md` 已有完整的 `web_list` / `rss` 配置规范与本地跑通示例。跑 2 周对照，确认覆盖度后停用对应 `mp_account`。
- **预期收益**：
  - 直接省 **¥310.80/月**（6 个 wxid 号合计 74 次/天）；
  - 官网数据有明确的发布时间与稳定 URL，**数据质量优于公众号**（避开「无可信时间不公开」和旧文规则）；
  - 零凭证、零风控、零版权争议，完全复用 hot-news 已有的 46 个 `web_list` 采集器与全套治理；
  - 完全符合项目架构偏好——现有 89.3% 的信源就是这么做的。
- **主要风险**：少量公众号独家内容会漏（可用「保留 1~2 个号 + 其余迁走」的混合方式兜底）；需要为每个站点写并维护选择器，站点改版时要跟着调。
- **优先级**：**P1，与方案 0 并行，是本次「增效」部分的主力。**

### 方案 2｜混合分层：付费保时效 + 自建保全量 ⚖️ P1 试点 → P2 决策

- **适用场景**：确实需要「去 Dajiala 依赖」，但仍要保住核心号的时效与官方一手身份。
- **动作**：
  1. 保留 2 个天合富家 `T1_5` 官方号走 Dajiala（30 次/天 = **¥126.00/月**，若都调到 120min 则 **¥100.80/月**）；
  2. 部署 WeRSS（MIT）单容器，把 6 个 T2 号配成 RSS；
  3. 在 hot-news 侧新增 6 条 `rss` 源，`feedUrl` 指向自建网关——**不需要改 hot-news 代码**，直接复用现成的 `rss` kind。
- **预期收益**：付费降至 **¥100.80~126.00/月**（省 **¥310.80~336.00/月**），同时把自建的运维面压缩到「一个容器 + 一组凭证」。
- **主要风险与接入摩擦（必须逐条处理）**：
  - `rss.ts:127` 正文判定：RSS 若只给摘要，hot-news 会**回头抓 `mp.weixin.qq.com` 原文页**，很可能失败 → 要么让网关输出 ≥280 字的正文但**只在站内用于结构化，不展示全文**（合规边界需再确认），要么显式接受 `bodyStatus: pending`；
  - `publishedAt` 必须带时区且可信，否则条目不公开；建议给每条 `rss` 源配 `publishedAtUtcOffset: "+08:00"`；
  - 时效从 60~240 分钟退化到小时级，需在后台观察是否影响日报出刊；
  - 凭证过期告警要接进现有飞书通道（`FEISHU_CONTENT_PUSH_ENABLED` 已开启）；
  - 容器默认口令、内网暴露面、AK 鉴权需一并加固。
- **优先级**：**P1 先做 2 个号的双跑试点（2 周）**，用实测的扫码频次、抓取成功率、入库条数、时间偏差决定是否推广；不试点不推广。

### 方案 3｜全量自建：彻底去掉按次计费 🔧 P2（条件触发）

- **适用场景**：号数量将大幅扩张（例如从 8 个扩到 30+），或组织层面明确要求不得依赖第三方数据商。
- **动作**：在方案 2 基础上停用全部 `mp_account`，8 个号全走自建 RSS；或改用 `POST /api/ingest/items` 推送（但需先扩展 `ItemIn` 以支持正文字段，且自动建的 `external` 源默认 `isolated`，要人工改 `editorial`）。
- **预期收益**：付费归零（省 **¥436.80/月 / ¥5,314.40/年**），号数越多边际成本越低。
- **主要风险**：
  - 失去付费回执、预算熔断、cursor、`fetch_runs` 等治理能力——需要把可观测性补回自建侧；
  - 微信凭证是**单点故障**，过期即全站断更；wechat-download-api 的 4 天周期意味着每月约 8 次人工介入；
  - AGPL-3.0（方案 B）对公开站点的许可义务；
  - 全文能力在 hot-news 合规规则下**不能用于展示**，自建的一半价值被削掉。
- **优先级**：**P2 条件触发**。触发条件写成硬指标：号数 ≥ 20，或月度付费 > ¥1,000，或供应商连续 2 个月可用性 < 99%。

### 方案 4｜直接接入 Wechat2RSS / RSSHub / 搜狗系 ❌ 不推荐

- **适用场景**：无。
- **排除依据**：Wechat2RSS 双阻断（禁商用 + 行业覆盖 0）；RSSHub 微信路由限额约 15 次/日且依赖第三方镜像；搜狗系接口被屏蔽、只给最近 10 条与临时链接、时间常缺。
- 若仅用于**内部研究 / 人工线索发现**（不进公开站点、不分发），Wechat2RSS 公开服务可作为零成本补盲，但需明确标注「仅个人学习研究」，且不得进入 hot-news 生产链路。

## 5. 推荐结论与决策依据

### 5.1 推荐路径

> **方案 0（立即） + 方案 1（P1 主推） + 方案 2（P1 双跑试点） → 视试点数据决定是否升级方案 3。**
>
> 不推荐一上来就全量替换，也不推荐接入任何免费公开 RSS 服务。

### 5.2 四条决策依据

1. **降本空间有明确天花板，且大头可能是空转。** 全量公众号付费 ¥436.80/月 ≈ ¥5,314.40/年，其中 6 个疑似配置错误的号占 **¥310.80/月（71%）**。修正配置 + 换公开源，几乎零成本就能拿到 **71% 的降本**；为剩下 29% 去建一套需要人工扫码的系统，边际收益很低。

2. **`docs/deploy.md` 自己给出的省钱顺序里，付费采集排在最后。** 原文顺序是：① 看「模型与评测」页找模型调用大头 → ② 关思考模式 → ③ 换便宜模型 → ④ 减少无关资料条数。示范数据里 **152 条资料用了约 930 次模型调用**，模型成本才是随条目数线性增长的主项。单纯砍掉 8 个公众号，对总账单的影响远小于优化模型调用。

3. **合规规则把自建方案的核心卖点关掉了。** 自建网关最强的能力是「全文 RSS + 图片代理 + 整号导出」，而 `docs/sources.md:224` 明写「公众号、付费墙内容不会因为技术上抓得到就获得全文展示」，`site_fulltext` / `syndicate_fulltext` 默认关。合规上只该用摘要 + 原文链接——这部分能力，现状的 Dajiala 链路和一条普通 RSS 都能给，不需要为此背一套凭证系统。

4. **风险是单向的。** 现状是「花钱买稳定、可追责、已接入治理」；替代方案是「省钱换凭证过期、账号风控、时效退化、AGPL 义务」。对一家对外公开的资讯站点，**断更和版权争议的成本远高于每年五千元**。项目里已有 67 个免费公开信源，说明架构本来就选择了低风险路线，没有理由为一个只占 10.7% 的信源类型反转这个选择。

### 5.3 什么时候应该改变结论

| 触发条件 | 应对 |
|---|---|
| 公众号号数扩到 ≥ 20 个 | 自建边际成本反超，启动方案 3 |
| Dajiala 连续 2 个月可用性 < 99% 或涨价 > 2× | 启动方案 3，把可观测性补回自建侧 |
| 试点显示 WeRSS 凭证 30 天内零人工介入且入库率 ≥ 95% | 可把方案 2 从试点扩到 6 个号 |
| 6 个 `wxid` 号经核实确无产出 | 立即停用，直接省 ¥310.80/月，方案 1 更划算 |
| 需要公众号全文用于站内检索（非展示） | 单独走法务评估，不要顺带改动 `site_fulltext` |

## 附录 A｜合规红线（不可协商）

1. `site_fulltext` / `syndicate_fulltext` 保持关闭；公众号只展示摘要 + 原文链接。
