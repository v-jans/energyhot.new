## 〇、执行摘要（先看结论）

1. **能力**：官网列出 46 个接口，公众号侧覆盖"当天发文 / 历史发文 / 文章详情 / 阅读点赞评论 / 账号主体与基础信息 / 搜一搜 / 搜狗长链"，另有视频号、贴图号及抖音小红书等全媒体接口。【官方】
2. **产品形态**：纯 HTTP API（POST 为主、个别 GET），`key` 放请求体，**按次计费、5 元起充**，标准接口 `post_history` ¥0.14/次、`article_detail` ¥0.03/次——与 hot-news 现有代码注释和实际扣费一致。【官方】【文档】
3. **数据来源的官方口径**：接口页原文"调用数据为腾讯官方实时数据"，接口文档反复强调"实时数据，非数据库陈旧数据"。**但官网没有任何一处说明这些数据如何获得、是否取得腾讯或公众号作者授权。**【官方】
4. **最重大发现——司法认定**：2021-09-15 杭州铁路运输法院 (2021)浙8601民初309号判决认定，"极致了"原运营方斯氏（杭州）新媒体通过爬虫绕开微信登录/IP 限制抓取公众号数据并对外提供，**构成不正当竞争**，判令停止抓取、删除数据、赔偿 60 万元、官网刊登声明 7 日；该案入选"2021 年中国十大最具研究价值知识产权裁判案例"。【司法】
5. **信息缺口（关键矛盾）**：现官网运营主体疑似已变更（页面出现"杭州阿楼第伍信息技术有限公司"），且仍宣称"腾讯官方实时数据"。**是否取得腾讯授权、现主体与判决被告的关系、技术路径是否已从爬虫改为合规授权，公开信息均无法证实。**【推测 + 缺口】
6. **落地建议**：hot-news 现有接入在**成本治理、幂等、可观测上是完整且正确的**，不需要重写。**第一优先级不是技术，是合规确权**——在拿到书面授权/合规说明前，把 `mp_account` 保持为可随时关停、不对外暴露全文、可审计的状态；技术上做四处加固（见第五节）。

### 1.2 接口契约细节【文档，来自官方 Apifox 的 `post_condition` 页】

- 请求体字段：`ghid`（公众号原始 ID）、`url`（文章链接）、`nickname`（公众号名）、`key`、`verifycode`（附加码）。三者 `ghid/url/nickname` 至少给一个（状态码 30001）。【文档】
- 返回字段：`data[].position`（发文位置 1-8）、`url`、`sn`（32 位 md5）、`post_time` / `post_time_str`、`cover_url`、`original`（0/1/2）、`item_show_type`（0 图文/5 视频/7 音乐/8 图片/10 文字/11 转载）、`digest`、`title`、`types`（9 群发/1 发布）；外层 `now_page`、`cost_money`、`remain_money`、`nickname`、`ghid`。【文档】
- **计价陷阱**：状态码 101（文章被删/账号被封/迁移）、104（原始 ID 不存在）**仍扣费**；缺 `key` 返回 10002；余额不足 20001；**QPS 上限 5 次/秒（-1）**。【文档】
- **最低消费**：官网原文"用户充值后，若累计十天内每日消费均不足 1 元，第十一天后每天消费金额如若未满 1 元，需补足 1 元进行扣费。若无调用行为，则不产生扣费。"【官方】——按次低频使用时这是隐性成本，须计入预算。
- API 功能与会员体系是两套独立计费体系，需分别付费。【官方】

### 1.3 典型业务流程【来自第三方技术文章的实例，非官方承诺】

第三方文章（jzl.com，与极致了同品牌的内容站）给出的 n8n 工作流：注册取 `key` → 浏览器 F12 从文章页找 `__biz` → 调 `post_history` 拿 `total_page` → 按页循环拉链接 → 逐篇调 `article_detail` → HTML 解析取正文 → 写文件/知识库。【报道】该流程与 hot-news `mp.ts` 的"列表 + 逐篇正文"两段式完全一致，说明 hot-news 的实现路径是行业通行做法。

## 二、数据来源与实现机制：三层证据

### 2.1 官方怎么说【官方】

- "调用数据为腾讯官方实时数据"（接口页顶部）。
- 各接口反复标注"该接口获取的是实时数据，非数据库陈旧数据"。
- 首页与定制页宣称"日处理 10 亿+ 实时数据""严格遵循各平台《服务条款》，采用动态反爬技术和人工复核机制，确保数据采集的稳定性与准确性"。【官方营销文案，与"腾讯官方数据"说法存在张力】

> 官网**没有**公开：数据是否来自腾讯官方授权接口、是否来自爬虫/群控、是否取得内容作者授权、数据保留多久。这是最大的信息缺口。

### 2.2 司法怎么认定【司法，(2021)浙8601民初309号】

法院基于公证证据认定（以下均为法院认定事实，非本文推测）：

- 抓取范围：公众号账号信息（头像/名称/微信号/简介/主体/名称记录）、文章信息（发文时间/位置/标题/链接/是否原创/阅读数/点赞数）、小程序信息。
- 技术手段：**"使用技术手段绕开微信客户端，从而获得了等同于'登录用户'的权限，同时使用自动化脚本不间断爬虫'爬取'"**；**"通过技术手段操控 75 个微信账号登录微信公众号并爬取数据……属于使用'拟人程序'爬虫工具"**；突破 IP 访问限制与封禁措施。
- 法律定性：**"违背诚实信用原则，擅自使用其他经营者征得用户同意、依法汇集且具有商业价值的数据，并足以实质性替代其他经营者提供的部分产品或服务……构成不正当竞争"**（《反不正当竞争法》第十二条第二款第四项）。法院明确指出这**损害了腾讯通过对外授权获取合作利益的商业利益**。
- 法院还特别指出："极致了"对抓取数据"仅通过简单统计和分析即对第三方提供……在技术上并没有明显创新性"，**"技术中立"抗辩不成立**。
- 判决结果：立即停止非法抓取、停止对外提供涉案数据服务、删除已存储数据、赔偿 60 万元（原 claims 300 万）、官网连续 7 日刊登声明。案件受理费 30,800 元中被告负担 18,480 元。
- 该案入选 2021 年中国十大最具研究价值知识产权裁判案例，被广泛作为"数据爬取边界"的标杆案例引用。

### 2.3 我们只能推测的部分【推测，须核实】

1. **现技术路径**：现官网仍运营、接口仍在线，且运营主体页面出现"杭州阿楼第伍信息技术有限公司"（而判决被告是斯氏（杭州）新媒体）。可能情形：(a) 主体变更 + 技术路径改为合规授权；(b) 主体变更但技术路径不变，只是尚未被再次追责；(c) 官网"腾讯官方实时数据"是营销话术。**公开信息无法区分，不能假设为 (a)。**
2. **"腾讯官方数据"的可能含义**：若属实，最可能是腾讯的某种商业数据合作/授权接口（类似新榜、清博的合规数据服务），而非 `mp.weixin.qq.com` 公开页面。但**官网未出示授权证明、未列出合作名称**。
3. **实现机制推断**：无论路径如何，产品必然包含一个服务端数据管道（账号发现 → 列表拉取 → 正文/互动补齐 → 结构化入库 → API 鉴权与按次计费）。hot-news 只需消费其 API，**不需要也不应该自己去复现这个管道**——见第五节风险控制。

## 四、对 hot-news 现状的核对结论

现有实现（`providers/dajiala.ts`、`sources/mp.ts`、`schedules.ts`）与上述官方契约逐项吻合：

- 接口路径、方法、`key` 放 body、`ghid ?? wxid` 传参、`mode=1` 取轻量正文——正确。【代码核对】
- 业务码处理：`-1` 限流重试、`20001` 余额、101/104/107 账号失效——与官方文档一致。【代码核对 + 文档】
- 成本治理：每账号每 10 分钟窗口一次列表回执去重、`cost_money` 记为 `basis: "actual"`、`remain_money` 写进 cursor、`budgets` 表按分钟/小时/天熔断、`pg_advisory_xact_lock` 串行化——**这套设计与官方"实时数据 + 按次计费 + QPS 5"的契约高度匹配，是全项目最健康的一块**。【代码核对】
- 安全阀：`COLLECT_ENABLED` + `DAJIALA_KEY` 双开关，未开启则无调度。【代码核对】

**结论：不需要重写采集层。** 唯一已知的配置风险仍是 8 个号里 6 个用 `wxid`（详见 `docs/wechat-source-options.md`），应优先修为 `gh_` 原始 ID，或改用 `history_by_ghid`（支持文章链接）作为兜底。

## 五、可落地实现方案

### 5.1 设计目标（按优先级）

1. **合规可审计**：任何时刻能回答"这条数据何时、由哪个接口、花多少钱、依据什么授权进入系统"。
2. **成本可控**：单账号间隔、全局预算、异常状态码的无效扣费都能被限制和观测。
3. **随时可停**：一个开关切断全部公众号采集，不影响站内其他 74 个信源。
4. **质量稳定**：正文缺失可重试、首次导入不刷屏、发布时间可信。

### 5.2 核心模块（映射到现有代码，标注"已有/新增"）

| 模块 | 职责 | 现状 |
|---|---|---|
| `providers/dajiala.ts` | 封装 `mpHistory` / `mpArticle`；业务码→错误类型映射；`cost_money` 回传 | **已有**，保留 |
| `providers/receipts.ts` | 幂等回执（logical_key = service:purpose:identity:window）、预算三窗熔断、unknown 恢复 | **已有**，保留 |
| `sources/mp.ts` | 每源调度、首次 7 天窗口、每轮最多 8 篇、正文缺失 3 次重试、入库与队列 | **已有**，保留 |
| `schedules.ts` | `sources.mp-reconcile` 每 15 分钟入队；双安全阀 | **已有**，保留 |
| **合规闸门模块（新增）** | 配置 `mp.data.useEnabled` + `mp.data.complianceNote`；未确认授权时只入库不公开；后台显示合规状态 | **新增** |
| **成本守护模块（新增）** | 无效扣费状态码（101/104）计数告警；`cost_money` 与预估价偏差告警；日/月累计上限 | **新增** |
| **授权凭证档案（新增，非代码）** | 保存供应商合同、授权说明、法务结论、复核日期、联系人 | **新增（流程）** |

### 5.3 关键流程

**正常采集流（已有，保持不变）**
```
cron */15 → scheduleMpReconcile() → 每个到期账号入 mpCheck 队列（singleton 去重）
  → mpHistory(ghid, {window: 10分钟桶}) → paidRequest 回执（复用则不扣费）
  → 按 post_time 倒序，跳过 >7天的首轮存量、跳过已知文章
  → 每篇 mpArticle(url) → paidRequest 回执 → sanitizeBody + stripTags
  → upsertMaterial（raw.dajiala 记 position/sn/original/cover）
  → queueProcessing（分析/精选/归组）
  → 更新 cursor（lastCheckedAt / lastPostTime / remainMoney）与 fetch_runs
```

**合规闸门流（新增）**
```
文章入库时 → 读 mp.data.useEnabled
  ├─ false（默认，未确权）→ participation_mode 强制 isolated，不进任何公开出口
  └─ true（法务确认后）→ 维持源自身 participation_mode
任一时刻改为 false → 后台一键把全部 mp_account 置 isolated（不删历史，只停公开）
```

**成本守护流（新增）**
```
paidRequest 记录 cost_money / cost_basis=actual
  → 状态码 101/104（仍扣费）单独计数 → 连续 N 次 → 告警 + 自动禁用该源
  → 日累计 > 阈值（建议 ¥50）→ 熔断当日剩余调用，告警
  → 月累计 / remain_money 低于阈值 → 告警充值
```

### 5.4 数据与权限设计

- **凭证**：`DAJIALA_KEY` 只存后端 `.env`（已在 `.env.example` 占位），前端不可见；附加码 `verifycode` 若启用一并入后端配置。【现有规则】
- **库表**：复用 `receipts` / `receipt_attempts`（记录每次调用的 request/response/cost/latency、unknown 状态）、`sources.cursor`（lastCheckedAt / remainMoney）、`articles.raw->dajiala`（抓取元数据与重试次数）、`fetch_runs`（每轮 found/new/error）。【已核实】
- **新增配置**（写 `site/` 或 settings，不写共享代码）：`mp.data.useEnabled`、`mp.compliance.reviewedAt`、`mp.compliance.contact`、`mp.cost.dailyLimit`；按 `AGENTS.md` 要求同时更新 `.env.example` / 文档，**不进共享提示词模板**。
- **权限**：仅管理员可在后台启停 `mp_account` 与查看回执明细；公开内容匿名，与访客看到的一致。【项目硬规则】
- **全文**：`site_fulltext` / `syndicate_fulltext` 保持关闭，公众号只显示摘要 + 原文链接——这既是项目规则，也正好回应司法判决里"实质性替代"的核心指控，是最重要的合规缓冲。【现有规则 + 司法启示】

### 5.5 风险控制

| 风险 | 等级 | 应对 |
|---|---|---|
| 供应商数据来源合法性（司法判例在前） | **高** | G1/G2 未确认前，`mp.data.useEnabled=false`，仅隔离区入库；取得书面合规说明 + 法务签字后再开 |
| "实质性替代"型侵权（判决核心理由） | **高** | 不展示全文、不提供检索/排行、不做内容再分发；只做热点发现，链接回原文 |
| 无效扣费（101/104 仍收费） | 中 | 修 wxid→ghid；新增状态码计数与自动禁用 |
| 最低消费与预算超支 | 中 | 全局三窗熔断 + 日上限 + 余额告警；低频时评估周级批量拉取 |
| QPS 超限（-1） | 低 | 现有队列并发限 2，远低于 5/s；保留退避重试 |
| 供应商停服/涨价 | 中 | 保持 `mp_account` 与 `rss`/`web_list` 双轨，按 `docs/wechat-source-options.md` 的 P1 用官网免费源替换 T2 媒体号 |
| 凭证泄露 | 中 | 后端 `.env`、不提交、定期轮换、附加码 |

### 5.6 实施步骤

- **阶段 0（立即，0 开发）**：核对 6 个 `wxid` 源的 `fetch_runs` 产出；无产出则改 `gh_` 或停用——最多止损 ¥310.80/月。
- **阶段 1（合规确认，1-2 周）**：向供应商索取 G1-G5 材料；法务出具能否用于公开站点的结论；结论未出前维持所有 mp 源 `isolated`。

## 六、结论

**技术上：现状已经是对的，不必重写；把配置修对、把两个守护模块补上即可。**

**合规上：这是本次调研真正的红线。** 一家因同类服务被生效判决认定构成不正当竞争、被责令停止抓取并赔偿的供应商，其"腾讯官方实时数据"的说法没有任何公开授权证据支撑。在 G1/G2/G5 与法务意见到位之前，正确的产品决策不是"优化接入"，而是**保持隔离、限制公开、随时可停**。这与此前几轮调研的结论一致：合规规则（`docs/sources.md:224`）已经削掉了这类数据源最有价值的"全文展示"能力，剩下的是低价值、高法律风险的"热点发现"用途——它值得保留，但不值得为它承担未经确认的合规敞口。
